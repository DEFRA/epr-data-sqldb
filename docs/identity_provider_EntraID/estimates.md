# Entra ID / B2C identity migration estimates

## Scope and estimate conventions

The per-object notes and person-day ranges are in [`regulator_identity_stored_in_Synapse.md`](regulator_identity_stored_in_Synapse.md). They assume an authoritative B2C-to-Entra mapping is supplied and both external IDs must resolve to the **same existing integer `rpd.Users.Id`**. The inventory estimates cover changes to checked-in Synapse objects and focused tests, not obtaining the mapping or implementing the migration. `0–0` means no incremental change to that object under this approach, not that dependent refresh and validation are free. Conditional ranges are additional alternatives, not automatic work. Similar rows for different columns of the same procedure/view are the same work item and must not be added twice. Downstream materialized tables generally depend on the source fix rather than needing separate mapping changes.

Simple lookup changes are estimated at **1–2 days** (approximately one day plus uncertainty), more complicated views at **2–3 days**, and very complex views at **3–4 days**. These are person-days, not elapsed time or commitments. The provisional range for an object absent from the repository is only a placeholder pending discovery; it is not evidence that a deployed object needs changing. Existing usage and production-data claims in the inventory are not independently verified.

## Proposed compatibility design and shared work

Keep `rpd.Users.Id` as the account/person key and preserve `rpd.Users.UserId` and raw historical event, submission, audit and file IDs. Introduce a mapping-backed `rpd.v_Users` (or equivalent alias lookup) that exposes one row per distinct accepted external identifier, each linked to the existing `Users.Id`. Update external-ID lookup/join sites to use the alias key, then join persons and memberships via the stable integer ID. Keep existing projected actor IDs unchanged unless the consumer contract explicitly asks for a separate resolved ID. An alias view may contain multiple rows per `Users.Id`: **never replace an internal-ID-only user join with a join to all alias rows**, since it would multiply results. For an external-ID join, ensure one matching account per lookup key and explicitly deduplicate the case where a mapping's legacy and current ID coincide.

| Shared work item | Incremental person-days | Scope and dependencies |
| --- | ---: | --- |
| Mapping storage and alias view | 1–2 | Define, load and expose the supplied mapping in Synapse with unambiguous aliases and testable error handling. Assumes mapping schema, population, owner and load mechanism are already agreed and available; delivery, identity proofing, ongoing synchronization and operational infrastructure are excluded and need separate estimates. |
| Shared migration reconciliation and regression | 1–2 | Test mapping, historical attribution, authorization scenarios, summary refresh counts/keys and rollback across the changed objects; local object-focused checks are included in each object's range. |
| Shared report refresh/reconciliation | 1–2 | Rebuild/reconcile affected materializations, names, statuses and security scope, once for the chain rather than once per table. Confirm orchestration and checkpoint behavior; estimate excludes changes required by unexpected deployed dependencies. |
| `dbo.v_POM_Submissions` and `dbo.v_POM_Submissions_R8` | 1–2 | Additional downstream work linked to `v_PersonOrganisationConnections.Users_UserId`: resolve both the account-side and file-metadata external IDs to the same `Users.Id`, preserving the compliance-scheme bypass and checking missing and duplicate matches. Do not expand the connection view per alias. |

Do not sum all inventory ranges: count the shared items once; include only applicable conditional changes, deduplicate repeated objects, and assess unavailable/deployed-only objects separately. These figures are intentionally not a whole-program total. Changes to token issuance, application authentication, API authorization, mapping provisioning, infrastructure, production data remediation, Power BI or other unverified consumers are not included.

## Data flow and implementation details

### Caller identity and nation

The three `apps.sp_FilterAndPaginate…` procedures resolve supplied `@RegulatorUserId` through `rpd.Users.UserId` → `Persons.UserId = Users.Id` → `PersonOrganisationConnections` → organisation/enrolment/service role with `ServiceId = 2`, then filter their summary CTEs by nation. Point each external-ID lookup at the alias key, keeping the person join on `Users.Id`. `InitialFilter`, JSON decision overlays and pagination should retain their existing behavior. The API request contains a GUID and `StoredProcedureExtensions.ToProcParams` forwards it as `@RegulatorUserId`; the reviewed path does not establish that this value is bound to the authenticated principal. Verify caller binding, tenant/issuer and authorization independently.

`dbo.sp_FilterAndPaginateOrganisationRegistrationSummaries` instead accepts `@NationId`; the checked-in API calls its `_resub` variant. Both SQL variants allow `NationId = 0`, and `_resub` also permits an application-reference match from another nation. The reviewed API rejects zero. Verify deployed authorization and intended behavior; this is not proof of an exploitable path and is not included in the mapping estimates.

### Historical actors and summary refreshes

`rpd.SubmissionEvents.UserId`, its distinct `RegulatorUserId`, `rpd.Submissions.UserId`, audit IDs and file-metadata IDs are historical values, not interchangeable with the current caller. `apps.v_OrganisationRegistrationSummaries` takes its regulator decision actor from event `UserId`, and its submitted actor from `rpd.Submissions.UserId`; it carries these values rather than resolving every actor through users. Its materialized table/merge and the detail procedures can retain raw IDs. If a consumer needs resolved actor `Users.Id` values, add separate fields and joins and apply the conditional ranges in the inventory.

`apps.v_SubmissionsSummaries` and `apps.v_RegistrationsSummaries` inner-join the submitted-event actor to users, persons and connections. An unmatched alias can remove source rows. Their `sp_AggregateAndMergePomData` and `sp_AggregateAndMergeRegistrationData` refreshes delete target rows absent from source. Snapshot and reconcile keys and counts before and after a controlled refresh; underlying events are not deleted by these merges. The complex `dbo.V_FetchOrganisationRegistrationSubmissionDetails_resub` has its own submitter-to-user join; its detail table supplies actor IDs to the detail procedure, while the summary-table join provides `RegistrationJourney`.

### Reporting, file metadata and notebooks

`dbo.v_cosmos_file_metadata` and `dbo.v_cosmos_file_metadata_CS_additions` resolve file-metadata user IDs to active users/profile data; preserve current deletion semantics while supporting both aliases. In addition, `v_cosmos_file_metadata.RankedData` compares the raw metadata ID to the current external ID projected by `v_enrolment_history`. Resolve both sides for that history match and preserve its date and row-number semantics; fixing only the later profile join would leave historical role attribution wrong. `dbo.v_submitted_pom_org_file_status` resolves decision-event `UserId` for a regulator name, with downstream status/name materializations. `dbo.v_Enrolmentstatus` resolves audit actor IDs to users for one branch; its rejected branch uses an internal person ID. The security view propagates that name to `t_rpd_data_SECURITY_FIX`; `v_POM_Submissions` reads the materialized security table. Enrolment, brand/partner, POM and comparison report tables mostly pass through names, statuses or comments; refresh them after source changes instead of counting each as a new lookup.

`dbo.v_Submitter_Name`, `dbo.v_enrolment_history` and `dbo.v_PersonOrganisationConnections` join persons to users by integer `Users.Id` and project the current external ID; they are not external-ID lookups. However, `v_POM_Submissions` and `v_POM_Submissions_R8` compare that projected external ID with raw file metadata. If the two are different aliases for the same person, an inner join may omit the direct-producer row: resolve both sides, preserve the compliance-scheme bypass, and check row cardinality. `v_CompanyBrandPartnerFileUploadSet` projects the raw metadata ID rather than performing a user lookup.

`epr-data/notebook/get_rpd_files.json` groups by the submitted-event `UserId`; `get_rpd_files_no_split.json` groups by the antivirus-result event's `UserId`. Neither is established as a user lookup. Retain the raw group key unless a new canonical output is required; changing the group key can change aggregation semantics. The prior `master_script_automation` finding of an event-to-user join is historical: that notebook and pipeline are absent from this checkout, and its deployment/output were not verified. If in use, inspect and separately estimate its alias-aware join.

`GenerateTableFromView` refreshes many report tables, but uses checkpointed stages. Its security/POM dependencies appear cyclic across runs, and a resumed checkpoint can skip earlier stages. Confirm the deployed orchestration and reconcile security/nation results rather than assuming one refresh produces a consistent fixed point. The `_ar` status view and the two `t_CV_Static_…` tables in the inventory were not found in checked-in SQL; inspect deployed definitions before estimating implementation confidently. Some inventory names differ from checked-in report columns, as noted in the relevant rows.

## Decisions and release checks

1. Confirm mapping authority, schema, delivery, approval and lifecycle. Validate coverage, aliases where old and new IDs are equal, duplicates, unmapped users, deleted/invited accounts, and historical users. Do not infer identity from email or name alone.
2. Define provider/tenant scope and ID selection. Existing request and historical columns contain GUIDs without provider metadata; prove each accepted GUID identifies exactly one user or extend the trusted contract to supply scope. Fail safely on ambiguous IDs.
3. Test old and new IDs resolving to the same internal `Users.Id`, person, regulator service membership and nation; test missing users/persons, disabled records, multiple qualifying memberships and cross-tenant inputs. Decide deleted/status and multi-nation policy explicitly rather than inheriting accidental SQL behavior.
4. Capture summary and report counts/keys and historical names before refresh. Verify matched, missing and duplicate aliases, compliance-scheme bypass, downstream materializations, security scope and rollback; stop before a destructive merge if reconciliation fails.
5. Confirm live Accounts-to-Synapse ingestion/control-file configuration, mapping freshness, deployed procedure versions, API caller binding, notebook and report owners, and actual Power BI bindings. Static source analysis alone cannot establish any of these.

Any historical-ID rewrite, additional canonical columns in facts/reports, contract changes to carry provider scope, or remediation of unverified consumers is additional scope and requires re-estimation.
